# UGC Surveys

Тестовое задание: создание пользовательских опросов, прохождение с сохранением
прогресса и статистика ответов.

Python 3.13 · Django 5.2 LTS · DRF 3.16 · PostgreSQL 17 · Uvicorn · uv · Docker Compose.
Точные версии зависимостей — в `uv.lock`.

## Локальный запуск

Нужны Docker и Docker Compose. Внешние сервисы не используются.

```sh
cp .env.example .env
# Замените DJANGO_SECRET_KEY и POSTGRES_PASSWORD в .env.
# Секрет можно сгенерировать: openssl rand -hex 32

docker compose build
docker compose up -d db
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py createsuperuser
docker compose up -d web
```

Откройте [админку](http://127.0.0.1:8000/admin/) и войдите под созданным суперпользователем.
Пароли и учетные записи администратора в репозитории отсутствуют.
При запуске web собирается статика админки. В локальном примере она обслуживается
Django; для продакшена статику следует передать веб-серверу.

## Управление через админку

- **Пользователи**: стандартная Django-форма создания и редактирования пользователя,
  установка пароля и прав. Вход в админку требует `is_staff` и соответствующих прав.
- **Опросы**: автор, название, `is_published`. Вопросы добавляются строками на странице
  опроса. Ссылка у существующего вопроса открывает страницу его редактирования.
- **Вопросы**: текст, позиция, разрешение собственного ответа; варианты добавляются
  строками на странице вопроса.
- **Позиция**: положительное число; меньшая позиция идет раньше. Пустая позиция
  нового элемента назначается автоматически. Позиции внутри одного родителя
  уникальны. Можно поменять местами две строки в одной форме.
- **Статистика**: ссылка в списке или на странице опроса. Количество стартов,
  завершений, ответов, среднее время, распределение вариантов и популярные ответы.

`is_published` определяет видимость для участников, по умолчанию `False`.
Автор может получать вопросы своего скрытого опроса. Публикация не запрещает
редактировать содержание и порядок; статусов и архивации нет.
Ответы привязаны к ID: перестановка не меняет выбор и не сбрасывает прогресс.
История текстов не хранится: статистика использует текущие названия вопросов/вариантов.

Пользователи, опросы, вопросы и варианты создаются и редактируются через админку.
API предоставляет список и детализацию опросов только для чтения, а также прохождение. Для пользователя-участника получите токен:

```sh
docker compose run --rm web python manage.py drf_create_token participant_username
```

Для готового примера с двумя пользователями и опросом «Овощи» есть необязательная
команда `seed_demo`. Она выведет токены и ID опроса; повторный запуск не сбрасывает ответы.
Это загрузка примера через ORM, а не отдельный интерфейс управления.

```sh
docker compose run --rm web python manage.py seed_demo
```

## API прохождения

Доступны список и детализация опросов, получение следующего вопроса и отправка ответа:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/surveys/` | Список доступных опросов с cursor-пагинацией по 20 записей |
| GET | `/api/v1/surveys/{survey_id}/` | Детализация опроса |
| GET | `/api/v1/surveys/{survey_id}/next-question/` | Получить следующий неотвеченный вопрос |
| POST | `/api/v1/participations/{participation_id}/answers/` | Отправить ответ |

Список и детализация содержат `questions`, а каждый вопрос — `choices`:
вложенные ответы здесь означают варианты выбора, без ответов других участников.
Вопросы и варианты идут в порядке `position`. Видны опубликованные опросы
и свои скрытые; просмотр списка/детализации не создает прохождение.
Ссылки `next`/`previous` позволяют перемещаться по страницам списка.
Создание, изменение и удаление через API недоступны.

Идентификация — штатный DRF `TokenAuthentication`, заголовок
`Authorization: Token <token>`. Регистрация, логин и восстановление пароля в API
не реализованы. Для внешнего доступа с токенами потребовался бы HTTPS;
Compose публикует локальный HTTP только на `127.0.0.1`.

Первый запрос следующего вопроса создает прохождение и фиксирует время начала.
Повторный запрос возвращает прежнее прохождение. Отдельного `/start/` нет.

```sh
API=http://127.0.0.1:8000/api/v1
TOKEN=token_from_command
SURVEY_ID=1

curl -sS -H "Authorization: Token $TOKEN" \
  "$API/surveys/$SURVEY_ID/next-question/"
```

Ответ содержит `participation_id`, прогресс `{answered, total}` и следующий вопрос
с вариантами. Подставьте ID из ответа:

```sh
PARTICIPATION_ID=1
QUESTION_ID=1
CHOICE_ID=1

curl -sS -X POST -H "Authorization: Token $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"question\":$QUESTION_ID,\"choice\":$CHOICE_ID}" \
  "$API/participations/$PARTICIPATION_ID/answers/"
```

Для собственного ответа вместо `choice` передайте `custom_text`, если у вопроса
включен `allow_custom_answer`. Пример тела:

```json
{"question": 2, "custom_text": "Только в салате"}
```

Принимается один вариант **либо** непустой текст до 2000 символов.
После ответа повторите GET следующего вопроса. После последнего ответа:
`state: completed`, `question: null`. Один пользователь имеет одно прохождение опроса.
Повтор одинакового ответа возвращает прежний ID с HTTP 200; первый прием — 201.

Ошибки: стандартный 400 — неверный ответ, ответ вне очереди, попытка заменить
принятый ответ, пустой опрос или конкурентное удаление вопроса/варианта;
401 — неверный/отсутствующий токен; 404 — недоступный опрос или чужое прохождение.
Отдельного класса Conflict и собственного формата ошибок нет.
Скрытие и возврат видимости сохраняют прогресс. Завершенные прохождения
не открываются заново при добавлении вопросов. Если автор удалил оставшиеся
неотвеченные вопросы, следующий вопрос отсутствует, а дата завершения не выдумывается.
Удаление данных с собранными ответами ограничено `PROTECT`.

## Модели и логика

`User(AbstractUser)`, `Survey`, `Question`, `Choice`, `Participation`, `Answer`.
Одна модель — один файл в `apps/<app>/models/`. У моделей есть русские
`verbose_name`, `verbose_name_plural`, названия полей и `__str__`;
унаследованные поля пользователя переводятся штатной локализацией Django.

Автоматическое назначение позиций, блокировки при сохранении/удалении структуры
и начало прохождения находятся в моделях. Админские формы проверяют весь набор
позиций вместе, PostgreSQL обеспечивает отложенную уникальность при перестановке.
Ответ блокирует только строку одного прохождения, а не общую строку опроса.
Статистика рассчитывается SQL-агрегациями по согласованному снимку REPEATABLE READ,
без отдельной таблицы счетчиков. Среднее время включает паузы и считается только
по завершенным прохождениям; без завершений равно `null`. При равенстве числа
ответов все лидирующие варианты считаются популярными.

## Проверки

```sh
docker compose run --rm --user root web sh -c \
  'uv sync --locked && uv run ruff check . && uv run ruff format --check . && uv run python manage.py check && uv run python manage.py makemigrations --check --dry-run && uv run python manage.py test --noinput'
```

Тесты используют PostgreSQL; учетной записи БД нужно право создавать тестовую БД.
Проверяются вложенные список/детализация, пагинация, права, ограничения БД, API
прохождения, повторная отправка, статистика и конкурентные записи.
URL в тестах формируются через reverse; тестов админки нет.
GitHub Actions выполняет тот же набор проверок с временной PostgreSQL.

Без Docker: Python 3.13, uv, доступная PostgreSQL с адресом в `.env`;
`uv sync --locked`, затем `uv run --env-file .env python manage.py migrate`,
`uv run --env-file .env python manage.py createsuperuser`,
`uv run --env-file .env python manage.py collectstatic --noinput`,
`uv run --env-file .env uvicorn config.asgi:application --lifespan off`.

Остановка с сохранением данных: `docker compose down`.

## Нагрузка и границы

Из ТЗ получается 15 млн вопросов, 75 млн вариантов, 75 млн прохождений
и до 1,125 млрд ответов. BigAutoField, составные индексы и `NOT EXISTS`
по ответам конкретного прохождения ограничивают объем чтения следующего вопроса.
Варианты загружаются только для него; глобальных счетчиков на записи ответа нет.

Uvicorn запускает ASGI-приложение. DRF/ORM остаются синхронными с короткими
транзакциями; `CONN_MAX_AGE=0`, workers задает `WEB_CONCURRENCY`.
ASGI сам по себе не доказывает ускорение. Популярные опросы потребуют измерений
стоимости статистики, хранения и индексов; пулы, агрегаты и партиционирование
не добавлялись заранее. Нагрузочный тест на расчетном объеме не выполнялся.
Продакшн-стенд и внешние сервисы не поднимались. Актуальная архитектура — в `plan`.
